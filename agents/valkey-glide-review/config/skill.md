# valkey-glide reviewer skill

Repository knowledge for reviewing `valkey-io/valkey-glide` pull requests. The grep hazards in the system prompt come first; this adds the layout and the contracts behind them. Facts here were checked against `main`. Where the code at the PR head disagrees, the code wins: cite the code, not this file.

## Bindings and how they reach the core

| Client | Native code | Mechanism | Path to the core |
|--------|-------------|-----------|------------------|
| Python async | `ffi/` (crate glide-ffi), plus a PyO3 module in `python/glide-async/src/lib.rs` | CFFI | Requests through FFI calls, responses over an anonymous pipe |
| Python sync | `ffi/` | CFFI | Direct FFI calls |
| Java | `java/src/` (crate glide-rs) | JNI | Direct JNI calls. A command crosses as its protobuf `RequestType` number plus arguments, the connection request as protobuf bytes |
| Node.js | `node/rust-client/` | napi-rs 3 | Direct NAPI calls. TypeScript builds `command_request.Command` objects and passes the request type and arguments; routes and the connection request cross as protobuf bytes |
| Go | `ffi/` | CGO, with `lib.h` generated by cbindgen | Direct FFI calls |
| Rust | `rust/` (crate valkey-glide, library `glide`) | Rust | Links `glide-core` directly |
| PHP, C#, Ruby, C++ | sibling repos | their own native layers on this repo's crates | Pinned as a git submodule |

Shared Python code (config, commands, exceptions, the CFFI declarations in `glide_shared/_glide_ffi.py`) lives in `python/glide-shared/`. Its PyO3 module `python/glide-shared/src/lib.rs` parses FFI responses and mirrors the `CommandResponse` struct from `ffi/src/lib.rs` field by field. A change to that struct must update both, and the CFFI declarations.

## Core architecture (`glide-core/src/`)

### Client

```rust
pub struct Client {
    shared: Arc<ClientShared>,
    iam_token_manager: Option<Arc<crate::iam::IAMTokenManager>>,
    otel_metadata: Arc<types::OTelMetadata>,
}

pub enum ClientWrapper {
    Standalone(StandaloneClient),
    Cluster { client: ClusterConnection, _cert_material_manager: Option<Arc<CertReloadManager>> },
    Lazy(Box<LazyClient>),
}
```

`Client` derefs to `ClientShared`, which holds the `Arc<RwLock<ClientWrapper>>`, the request timeout, the inflight counter and limit, the compression manager, the pubsub synchronizer, the optional client-side cache and circuit breaker, the current database, and the pool and IAM bookkeeping. Cloning a `Client` per command is a refcount bump, so code that clones it is not copying state. Fields that must be shared across clones live behind `Arc` in `ClientShared`.

A client created with `lazy_connect` starts as `ClientWrapper::Lazy` and becomes `Standalone` or `Cluster` on the first command, through `get_or_initialize_client()`.

### Command path

`Client::send_command`:

1. Refreshes IAM auth first if IAM is configured (`reconcile_iam_before_dispatch`).
2. Connects a lazy client (`get_or_initialize_client()`).
3. Rejects the command if the client circuit breaker is open.
4. Picks the request timeout: the client default, or for blocking commands the command's own timeout plus `BLOCKING_CMD_TIMEOUT_EXTENSION` (0.5 s). A blocking timeout of 0 means no request timeout.
5. Takes an inflight slot with `reserve_inflight_request()`, or fails with "Reached maximum inflight requests".
6. Routes with the caller's routing or `RoutingInfo::for_routable()`, and dispatches to `StandaloneClient` or `ClusterConnection`.
7. Decompresses the response when compression is on, and runs post-command hooks: SELECT updates the tracked database, AUTH updates stored credentials.

Compressing the command's arguments happens before `send_command`, in each binding's own copy of `process_command_for_compression` (see the grep hazards).

### Runtime

`get_or_init_runtime()` (in `client/mod.rs`) starts one current-thread Tokio runtime on a dedicated OS thread named `glide-runtime-thread`, once per process. Every client in the process shares it, so a blocking call on that runtime stalls every client.

## Connections

### Multiplexing and inflight limits

Each node gets one `MultiplexedConnection`; requests pipeline over it. `DEFAULT_MAX_INFLIGHT_REQUESTS = 1000` (`client/mod.rs`, sized from Little's Law in the comment above it) caps concurrent inflight requests per client. `reserve_inflight_request()` decrements the counter and the returned `InflightRequestTracker` gives the slot back on drop. Inflight usage is logged at debug level every 10% of the limit.

### Timeouts

- Request timeout: `DEFAULT_RESPONSE_TIMEOUT` = 250 ms (`client/mod.rs`). Blocking commands are handled as in the command path above.
- Connection timeout: `DEFAULT_CONNECTION_TIMEOUT` = 2000 ms (`client/types.rs`). Client creation allows 500 ms on top.

### Standalone reconnection

`ReconnectingConnection` is used only by `standalone_client.rs`. Its `ConnectionState` is `Connected(MultiplexedConnection)`, `Reconnecting`, or `InitializedDisconnected`. On disconnect it moves to `Reconnecting`, resets `connection_available_signal` (a `ManualResetEvent`) so callers wait, and spawns a reconnect task. Retries follow the `RetryStrategy` backoff without end. Before each attempt it picks up a fresh IAM token and the latest mTLS certificate when those are configured, and each new connection is checked with PING before it is used. Reconnecting stops only on success or when the client is dropped.

During the initial connection these errors are not retried: `AuthenticationFailed`, `InvalidClientConfig`, `RESP3NotSupported`, and messages containing `NOAUTH` or `WRONGPASS`.

`ReconnectingConnection` replays connection state on reconnect. The `update_connection_*` methods keep it current: database (SELECT), password (AUTH, IAM refresh), username (AUTH), client name (CLIENT SETNAME), protocol (HELLO). A new piece of per-connection state needs the same treatment or it is lost on the first reconnect.

### Periodic checks

`CONNECTION_CHECKS_INTERVAL` = 3 s (`client/mod.rs`). Standalone watches for disconnects passively; the `standalone_heartbeat` feature adds a PING every `HEARTBEAT_SLEEP_DURATION` (1 s). Cluster clients always enable `periodic_connections_checks` at that interval.

### Read-only mode

`read_only` in `ConnectionRequest` (protobuf field 26) is implemented in `standalone_client.rs`. It skips primary discovery, blocks write commands, and defaults `ReadFrom` to `PreferReplica`. It is rejected with the AZ-affinity strategies and with node discovery mode `DISCOVER_ALL`.

### Separate connections

A multiplexed connection's state is shared by every caller on it. GLIDE gives callers other options:

- Isolated scopes (`scope.rs`) hand out dedicated connections for WATCH/MULTI/EXEC and CLIENT TRACKING. A scope inherits the parent's current database, credentials and compression.
- The client-instance pool (`pool.rs`) lends whole clients to the bindings. Release resets state with DISCARD and SELECT, and abandoned borrows are reclaimed after a timeout.
- Blocking commands (BLPOP, BRPOP, BLMOVE, XREAD BLOCK, ...) hold up everything behind them on the same connection, so they belong on a dedicated client.

### Custom commands

`custom_command()` uses `RequestType::CustomCommand` (1). The caller's arguments become the whole command, with the command name first.

## PubSub synchronizer (`pubsub/synchronizer.rs`)

`GlidePubSubSynchronizer` keeps `desired_subscriptions` (what the user asked for) apart from `current_subscriptions_by_address` (what each server address has confirmed). A reconciliation task closes the gap every `DEFAULT_RECONCILIATION_INTERVAL` (3 s) and whenever it is notified. `SyncDiff` holds what to subscribe and what to unsubscribe per address.

- Cluster supports exact, pattern and sharded subscriptions. Standalone supports exact and pattern.
- Triggers: a user subscribe or unsubscribe, a server push, the timer, and topology changes through `handle_topology_refresh(&SlotMap)`.
- On topology change, a disconnected address is cleared from the current state, subscriptions that moved are queued in `pending_unsubscribes` for the old node, and reconciliation subscribes on the new owner.
- The synchronizer holds the client as `OnceCell<Weak<TokioRwLock<ClientWrapper>>>`: weak to avoid a reference cycle, set once during init.
- `PubSubCommandApplier` (trait in `client/mod.rs`, implemented for `ClientWrapper`) sends SUBSCRIBE and UNSUBSCRIBE without knowing standalone from cluster. `MockPubSubSynchronizer` in `pubsub/mock.rs` mocks the whole `PubSubSynchronizer` trait for tests.

## Cluster (vendored `glide-core/redis-rs/`)

- `redis::cluster_slotmap::SlotMap` maps slots 0-16383 to nodes. It is built from `CLUSTER SLOTS` and refreshed on MOVED and periodically (`DEFAULT_PERIODIC_TOPOLOGY_CHECKS_INTERVAL` = 60 s). ASK is one-shot: send ASKING plus the command to the named node, without updating the map.
- Routing lives in `redis::cluster_routing`: single slot, all primaries, all nodes, random node, with a response policy for combining multi-node replies. Multi-key commands that allow it (MGET, MSET, ...) are split by slot and dispatched by GLIDE.
- `ReadFromReplicaStrategy` (in `cluster_slotmap.rs`): `AlwaysFromPrimary`, `RoundRobin`, `AZAffinity`, `AZAffinityReplicasAndPrimary`, `AllNodes`, `AZAffinityAllNodes`.
- Per-node connections and their reconnection belong to the vendored `ClusterConnection`, not to `ReconnectingConnection`.
- Non-atomic batch retries: `PipelineRetryStrategy` in `redis-rs/redis/src/pipeline.rs` has `retry_server_error` (may reorder execution) and `retry_connection_error` (may execute twice). MOVED and ASK are always followed regardless.

## Reviewer checklist: new commands

A new command usually touches all of these. Missing pieces are findings:

- `RequestType` in `glide-core/src/protobuf/command_request.proto` and in `glide-core/src/request_type.rs`, with its protobuf mapping and its `get_command()` arm. Numbers follow the category ranges (bitmap 1xx, cluster 2xx, ...).
- Response conversion in `client/value_conversion.rs` when the reply needs a shape other than the raw value.
- Each client: Node `node/src/Commands.ts` plus the client class; Python `python/glide-shared/glide_shared/commands/` and the async and sync command groups (`python/glide-async/python/glide/async_commands/`, `python/glide-sync/glide_sync/sync_commands/`); Java `java/client/src/main/java/glide/api/commands/` plus `BaseClient`; Go `go/interfaces/` plus `go/base_client.go`; Rust `rust/src/commands/`.
- Tests in each client's suite (`node/tests/`, `python/tests/`, `java/client/src/test/` and `java/integTest/`, `go/integTest/`, `rust/tests/`), including cluster mode when routing matters.
- Argument order and return types that match the other clients, or a stated reason they differ.

## Reviewer checklist: build and test

- What can run in the review container is listed in the Build section of the prompt. Rust crates build from their own directories; there is no workspace `Cargo.toml` at the root.
- Integration tests in every language need a running server (`utils/cluster_manager.py` starts one in CI). In the container, check behavior with unit tests or by reading.
- A change to `glide-core/` or `ffi/` should come with tests where the behavior is visible: unit tests in the crate, and tests in each binding whose contract it touches. Core-only tests do not show a binding is correct.
- CI runs a workflow per binding under `.github/workflows/`, formatters included. Formatting is not a review comment.
- Per-binding entry points CI uses, for reference when a PR changes them: the root `Makefile` (`java`, `python`, `node`, `go` and their `-test` and `-lint` targets), `go/Makefile` (`build`, `unit-test`, `integ-test`, `lint`; `build` compiles the FFI library and generates the protobuf code first), and `./gradlew` in `java/`. The review container runs only what the Build section lists.
